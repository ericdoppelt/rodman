- **Verify bull/bear web_search allocation isn't redundant with market context.** Each bull/bear call in `stockAgents.ts` gets one `web_search` (`max_uses: 1`), steered by prompt toward ticker-specific news ("Research `{ticker}` specifically"). But this is a soft instruction, not enforced — if the model's single query ends up broad (re-deriving general market conditions already passed in as text) instead of ticker-specific, that search is wasted. The full raw response (including `web_search_tool_result` / `server_tool_use` blocks) is now persisted per call in Supabase's `llm_calls` table — query a few real runs there to see what's actually being searched.

- **Backtest/eval harness (track 1 has results; track 2 still pending).** Two tracks exist, because `web_search` has no server-enforced date-restriction parameter (confirmed against current docs — only `max_uses`/`allowed_domains`/`blocked_domains`/`user_location`/`allowed_callers`/`response_inclusion` exist), so any backtest that reuses it leaks future information:
  1. `pnpm backtest` (`src/backtest/runBacktest.ts`) — swaps `web_search` for point-in-time Tavily search (`end_date` filter, see `docs/decisions/0007-tavily-and-daily-cache-for-backtest.md`) so bull/bear research can't see anything past the historical date, then runs the real, unmodified judge and scores picks vs. a buy-every-qualifying-dip baseline on actual forward returns. Raw inputs (candidates, index/sector data, news) are cached per date (`data/backtest-cache/`) so re-running against a different model only re-pays Claude token cost, not the full data-gathering pass. This only validates the judge's conviction-calibration logic — Tavily's index is still narrower than live web search, so it says nothing about whether the deployed research step is any good. Most recent 30-day run (seed 42, Sonnet judge, pre-Tavily/Polygon-news evidence): judge picks *underperformed* baseline at every horizon — primary 5-day: picks -1.33% avg / 50% win rate vs. baseline +2.75% avg / 55% win rate (n=10 picks / 120 candidates); 1-day and 20-day showed the same direction. This reversed an earlier, smaller run (n=23) where picks had beaten baseline — with only 10-23 picks per run, results are noisy and haven't been rerun yet against the new Tavily evidence. Caveats: (a) this validates the judge's decision logic only, not the deployed pipeline — production uses live `web_search`, which was thinner-evidence here by necessity; a good or bad backtest number doesn't mean the real pipeline performs the same. (b) 5-day is the pre-committed primary metric (catalyst relevance fades within about a week) — don't cherry-pick whichever horizon looks better in a given run. (c) n=10-23 picks is noisy, not statistical proof — a single run flipping the conclusion is itself evidence of high variance; a larger sample (now cheaper thanks to the daily cache) is needed before trusting either direction.
  2. `pnpm start` now logs every real production run to `data/forward-test-log.jsonl` (`src/backtest/logRun.ts`); `pnpm score-forward-test` scores logged runs once enough time has passed for a forward return. This is the only rigorous validation of the actual pipeline (real `web_search`, real research quality), since live search results are inherently non-replayable for past dates. Needs weeks of accumulated runs before the numbers mean anything — nothing to report yet. **Caveat now that `pnpm start` runs on a GitHub Actions cron (see below):** `data/` is gitignored and each Action run is an ephemeral checkout, so `forward-test-log.jsonl` entries from cron runs won't accumulate anywhere — only entries from runs on your own machine persist. Either migrate `scoreForwardTest.ts` to read from Supabase's `runs`/`picks` tables (which the cron *does* persist), or have the workflow commit `data/forward-test-log.jsonl` back to the repo.

- **Reasoning-quality grader, separate from outcome metrics.** The backtest currently only grades picks by what the stock actually did afterward (`getForwardReturns`) — it never checks whether the bull/bear/judge reasoning itself was sound. That's a real gap, not just a nice-to-have, especially at the small sample sizes the backtest runs at (outcome noise dominates before reasoning-quality signal would even show up in the numbers). Add a separate grading pass: feed a model the bull case, bear case, and judge's reasoning *without revealing the actual outcome*, and score things like whether conviction level matched the strength of evidence given, and whether bull/bear grounded claims in the provided news rather than going beyond it (hallucination check). This is additive to, not a replacement for, the outcome metrics — outcome tells you the payoff, this tells you whether a good outcome was luck or a sound process, which matters most for how well the pipeline generalizes to future situations it hasn't been tested on.

Wrapping distinct sections in XML tags (e.g. `<market_context>`, `<stock_data>`) is Anthropic's recommended pattern for helping the model reliably distinguish different kinds of input.
