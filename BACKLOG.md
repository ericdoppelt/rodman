- **Backtest/eval harness (track 1 has results; track 2 still pending).** Two tracks exist, because `web_search` has no server-enforced date-restriction parameter (confirmed against current docs — only `max_uses`/`allowed_domains`/`blocked_domains`/`user_location`/`allowed_callers`/`response_inclusion` exist), so any backtest that reuses it leaks future information:
  1. `pnpm backtest` (`src/backtest/runBacktest.ts`) — swaps `web_search` for point-in-time Tavily search (`end_date` filter, see `docs/decisions/0007-tavily-and-daily-cache-for-backtest.md`) so bull/bear research can't see anything past the historical date, then runs the judge and scores picks vs. a buy-every-qualifying-dip baseline on actual forward returns. Judge model defaults to `claude-sonnet-5` for backtest runs (cost control, see `docs/decisions/0008-sonnet-judge-for-backtest-cost-control.md`) rather than production's `claude-opus-5` — set `BACKTEST_JUDGE_MODEL=claude-opus-5` for a fidelity-matched run. Once warmed, a scoring run's day loop has no cross-day network dependency left, so the actual Claude research/judge work now runs `BACKTEST_CONCURRENCY` days at once (default 4) instead of processing dates serially — a cache miss still bottlenecks on Polygon's rate limit regardless, so warm the cache first for the full speedup. This only validates the judge's conviction-calibration logic — Tavily's index is still narrower than live web search, so it says nothing about whether the deployed research step is any good. Most recent 30-day run (2026-07-30, seed 42, Sonnet judge, first with Tavily evidence): judge picks underperformed baseline at the primary 5-day horizon — picks -0.56% avg / 38% win rate vs. baseline +2.03% avg / 54% win rate (n=8 picks / 120 candidates); 1-day showed the same direction (picks -1.96% vs. baseline -0.46%), but 20-day picks beat baseline (14.41% vs. 3.78%, 75% win rate) — a reminder not to cherry-pick horizons, not evidence 20-day is where the edge actually is. Caveats: (a) this validates the judge's decision logic only, not the deployed pipeline — production uses live `web_search`, which was thinner-evidence here by necessity; a good or bad backtest number doesn't mean the real pipeline performs the same. (b) 5-day is the pre-committed primary metric (catalyst relevance fades within about a week) — don't cherry-pick whichever horizon looks better in a given run. (c) n=8-23 picks per run is noisy, not statistical proof — a larger sample (now cheaper thanks to the daily cache) is needed before trusting any direction.

- **Reasoning-quality grader, separate from outcome metrics.** The backtest currently only grades picks by what the stock actually did afterward (`getForwardReturns`) — it never checks whether the bull/bear/judge reasoning itself was sound. That's a real gap, not just a nice-to-have, especially at the small sample sizes the backtest runs at (outcome noise dominates before reasoning-quality signal would even show up in the numbers). Add a separate grading pass: feed a model the bull case, bear case, and judge's reasoning *without revealing the actual outcome*, and score things like whether conviction level matched the strength of evidence given, and whether bull/bear grounded claims in the provided news rather than going beyond it (hallucination check). This is additive to, not a replacement for, the outcome metrics — outcome tells you the payoff, this tells you whether a good outcome was luck or a sound process, which matters most for how well the pipeline generalizes to future situations it hasn't been tested on.

- **`update-pick-price-series` refetches each pick's entire history every run instead of only new bars.** Fine at today's volume (1 pick/weekday, 2 total), but the real ceiling on refresh cadence is Polygon's free-tier 5-calls/min limit — one call per pick per run regardless of history size, so a full cycle takes `picks × 12s`. Switching to incremental fetch (only bars since each pick's last-stored point) shrinks payload/write size but does **not** raise that ceiling, since it's still one call per pick. To safely go more frequent than the current 30-min cadence as picks accumulate, the actual fix is scoping frequent refreshes to recent/"active" picks only and refreshing older, settled picks less often (e.g. once/day).
