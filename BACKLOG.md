# Backlog

## Open items

- **Verify bull/bear web_search allocation isn't redundant with market context.** Each bull/bear call in `stockAgents.ts` gets one `web_search` (`max_uses: 1`), steered by prompt toward ticker-specific news ("Research `{ticker}` specifically"). But this is a soft instruction, not enforced — if the model's single query ends up broad (re-deriving general market conditions already passed in as text) instead of ticker-specific, that search is wasted. The full raw response (including `web_search_tool_result` / `server_tool_use` blocks) is now persisted per call in Supabase's `llm_calls` table — query a few real runs there to see what's actually being searched.

- **Backtest/eval harness (track 1 has an initial result; track 2 still pending).** Two tracks exist, because `web_search` can't be restricted to a historical date (no such param exists), so any backtest that reuses it leaks future information:
  1. `pnpm backtest` (`src/backtest/runBacktest.ts`) — swaps `web_search` for point-in-time Polygon news (`published_utc.lte` filter) so bull/bear research can't see anything past the historical date, then runs the real, unmodified judge and scores picks vs. a buy-every-qualifying-dip baseline on actual forward returns. This only validates the judge's conviction-calibration logic — Polygon news snippets are much thinner than live web search, so it says nothing about whether the deployed research step is any good. First 30-day run (seed 42): judge picks beat baseline on both avg return and win rate at the primary 5-day horizon (picks -12.22% avg / 26% win rate vs. baseline -17.79% avg / 18% win rate, n=23 picks / 60 candidates), and the same direction held at 20 days. Caveats: (a) this validates the judge's decision logic only, not the deployed pipeline — production uses live `web_search`, which is thinner-evidence here by necessity; a good backtest number doesn't mean the real pipeline performs the same. (b) 5-day is the pre-committed primary metric (catalyst relevance fades within about a week) — don't cherry-pick whichever horizon looks better in a given run. (c) n=23 picks is directional signal, not statistical proof; bigger runs are bottlenecked by Polygon's free-tier rate limit, not cost.
  2. `pnpm start` now logs every real production run to `data/forward-test-log.jsonl` (`src/backtest/logRun.ts`); `pnpm score-forward-test` scores logged runs once enough time has passed for a forward return. This is the only rigorous validation of the actual pipeline (real `web_search`, real research quality), since live search results are inherently non-replayable for past dates. Needs weeks of accumulated runs before the numbers mean anything — nothing to report yet. **Caveat now that `pnpm start` runs on a GitHub Actions cron (see below):** `data/` is gitignored and each Action run is an ephemeral checkout, so `forward-test-log.jsonl` entries from cron runs won't accumulate anywhere — only entries from runs on your own machine persist. Either migrate `scoreForwardTest.ts` to read from Supabase's `runs`/`picks` tables (which the cron *does* persist), or have the workflow commit `data/forward-test-log.jsonl` back to the repo.

- **Reasoning-quality grader, separate from outcome metrics.** The backtest currently only grades picks by what the stock actually did afterward (`getForwardReturns`) — it never checks whether the bull/bear/judge reasoning itself was sound. That's a real gap, not just a nice-to-have, especially at the small sample sizes the backtest runs at (outcome noise dominates before reasoning-quality signal would even show up in the numbers). Add a separate grading pass: feed a model the bull case, bear case, and judge's reasoning *without revealing the actual outcome*, and score things like whether conviction level matched the strength of evidence given, and whether bull/bear grounded claims in the provided news rather than going beyond it (hallucination check). This is additive to, not a replacement for, the outcome metrics — outcome tells you the payoff, this tells you whether a good outcome was luck or a sound process, which matters most for how well the pipeline generalizes to future situations it hasn't been tested on.

- **No position sizing / risk management.** The pipeline recommends a bare ticker with no sizing, stop-loss, or portfolio-level risk logic.

- **Add few-shot examples for conviction calibration** (depends on backtest harness above). Once real graded cases exist, use them as few-shot examples to calibrate what "strong" vs "weak" conviction should look like. Risk: examples can bias toward the example's pattern (sector, evidence type) rather than per-case judgment — keep examples diverse.

- **Use XML tags to structure prompt context.** Bull/bear/judge prompts currently interpolate context (market conditions, stock data) as flat text. Wrapping distinct sections in XML tags (e.g. `<market_context>`, `<stock_data>`) is Anthropic's recommended pattern for helping the model reliably distinguish different kinds of input.

- **Add a custom tool** (e.g. let the model itself execute a trade or flag a rejected candidate, rather than the host code doing it after the fact). Currently only the server-side `web_search` tool is used, so there's no client-executed tool input to validate. Use `strict: true` on the tool definition to guarantee `tool_use.input` matches its schema, and Zod to type/parse it on the way in. (Picks/runs/LLM calls are now persisted to Supabase, but via plain host-side code in `index.ts` — not a model-invoked tool.)

- **Should this use prompt caching?** Not useful yet: Haiku 4.5's minimum cacheable prefix is 4096 tokens, and current system prompts (bull/bear/judge) are a few hundred tokens — well under. Also runs once/day, so cache TTL (5 min–1 hr) expires between runs regardless. Revisit once few-shot examples grow prompt size, or once the backtest harness is making many calls in quick succession against the same system prompt.

- **Enable Claude Code sandboxing to block `.env` reads at the OS level.** `.claude/settings.json` currently denies the `Read` tool on `.env`, but that doesn't stop `Bash` commands (`cat .env`, `grep`, `python -c ...`, etc.) from reading it. Real fix is `sandbox.enabled: true` with `.env` on `sandbox.credentials.files` (deny mode), which blocks the file at the filesystem layer regardless of which command tries to read it. Deferred because enabling sandboxing restricts *all* Bash network access to an explicit `network.allowedDomains` allowlist — needs every domain the pipeline/tooling actually hits (Polygon, Anthropic, Supabase, npm registry, GitHub) enumerated and tested first, or commands will just fail.

- **Retry judge/bull/bear calls on schema validation failure, feeding the error back to the model.** `stockPickSchema.ticker`/`.reasoning` and `stockAnalysisSchema.reasoning` now use `.min(1)`, so a malformed response (e.g. the judge returning `[{"ticker": "", "reasoning": ""}]` instead of `[]`, seen in a live test run) throws instead of silently persisting garbage — but the whole run just fails rather than recovering. Anthropic's structured-output constrained decoding doesn't enforce `.min(1)`-style refinements server-side (confirmed via docs: `minLength`/`pattern`/etc. are stripped and turned into field-description hints, not hard constraints), so the SDK's own post-hoc Zod validation (`zodOutputFormat`'s `.parse()`) is what actually catches this — meaning it's expected to recur occasionally. Add a bounded retry (e.g. 1-2 attempts) that appends the validation error to the next request so the model can self-correct, before giving up and failing the run.

- **Enable Row Level Security on the Supabase tables (`runs`, `llm_calls`, `picks`, `rejected_candidates`) before any client-facing UI ships.** Currently disabled — flagged by Supabase's advisor when the tables were created. Low risk today since only the `service_role` key is used (server-side/cron only), but required once a UI queries Supabase with the `anon` key, since RLS-off means anyone with that key can read/write every row. Needs policies added alongside `ENABLE ROW LEVEL SECURITY`, not just the bare enable (which would otherwise block all access).
