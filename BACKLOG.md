  1. `pnpm backtest` (`src/backtest/runBacktest.ts`) — swaps `web_search` for point-in-time Tavily search (`end_date` filter, see `docs/decisions/0007-tavily-and-daily-cache-for-backtest.md`) so bull/bear research can't see anything past the historical date, then runs the judge and scores picks vs. a buy-every-qualifying-dip baseline on actual forward returns. Set `BACKTEST_JUDGE_MODEL=claude-sonnet-5` for cost control (see `docs/decisions/0008-sonnet-judge-for-backtest-cost-control.md`) or `=claude-opus-5` for a deliberate fidelity-matched run. Raw inputs (candidates, index/sector data, news, and forward returns) are cached per date (`data/backtest-cache/`) so re-running against a different model only re-pays Claude token cost, not the full data-gathering pass. `pnpm warm-backtest-cache` (`src/backtest/warmCache.ts`) pre-populates this cache for every day in the sampling window with no Claude calls at all (Polygon + Tavily only, both free-tier) — run it overnight to build up a full year of cached days ahead of time, since Polygon's free-tier rate limit (5 calls/min) is what makes fetching a large date range slow, and it's a one-time cost per date once cached. Once warmed, a scoring run's day loop has no cross-day network dependency left, so the actual Claude research/judge work now runs `BACKTEST_CONCURRENCY` days at once (default 4) instead of processing dates serially — a cache miss still bottlenecks on Polygon's rate limit regardless, so warm the cache first for the full speedup. Caveats: (a) this validates the judge's decision logic only, not the deployed pipeline — production uses live `web_search`, which was thinner-evidence here by necessity; a good or bad backtest number doesn't mean the real pipeline performs the same. (b) 5-day is the pre-committed primary metric (catalyst relevance fades within about a week) — don't cherry-pick whichever horizon looks better in a given run. (c) n=8-23 picks per run is noisy, not statistical proof — a larger sample (now cheaper thanks to the daily cache) is needed before trusting any direction.
  2. `pnpm start` now logs every real production run to `data/forward-test-log.jsonl` (`src/backtest/logRun.ts`); `pnpm score-forward-test` scores logged runs once enough time has passed for a forward return. - **Reasoning-quality grader, separate from outcome metrics.** The backtest currently only grades picks by what the stock actually did afterward (`getForwardReturns`) — it never checks whether the bull/bear/judge reasoning itself was sound. That's a real gap, not just a nice-to-have, especially at the small sample sizes the backtest runs at (outcome noise dominates before reasoning-quality signal would even show up in the numbers). Add a separate grading pass: feed a model the bull case, bear case, and judge's reasoning *without revealing the actual outcome*, and score things like whether conviction level matched the strength of evidence given, and whether bull/bear grounded claims in the provided news rather than going beyond it (hallucination check). This is additive to, not a replacement for, the outcome metrics — outcome tells you the payoff, this tells you whether a good outcome was luck or a sound process, which matters most for how well the pipeline generalizes to future situations it hasn't been tested on.

- **Backtest's Tavily evidence is frequently irrelevant or stale — fix before trusting judge-quality conclusions from it.** Surfaced while investigating why an "eliminate obviously flawed candidates" judge variant (backtest-only, `BACKTEST_STRATEGY=eliminate`, see `eliminationJudge.ts`) kept two real disasters (TDTH: -67% on the day, still -68% a year later; BULL/Webull: -30% on the day, -73% a year later) while excluding 3 stocks that all did fine or great (FTAI +210%, PLUG +393%, CTRI +33% at 252d). Checked the actual cached evidence (`data/backtest-cache/*.json` → `perTickerNews`) both judge calls had to work with, and it was close to useless: TDTH's 5 articles were all about unrelated tickers/topics (Tavily just doesn't have real coverage of this obscure microcap), and BULL's 5 articles were all generic "bull market" pieces — the ticker collided with the common English word. A broader random sample of 17 more tickers found ~1/3 similarly polluted by short/common-word/acronym collisions (`CAR`, `Q`, `BE`, `WHD`, `EQPT`, `GPI` all pulled in results about unrelated companies or concepts). Separately, even a *good* match (CAVA) returned 5 articles all dated 4-8 months before the actual dip — Tavily's relevance ranking has no recency pressure against the wide-open `start_date: '2000-01-01'` in `fetchTavily.ts` (that was only ever set to work around a Tavily quirk where `end_date` is silently ignored without *some* `start_date` present — not a deliberate recency choice). And even on-topic articles are just Tavily's ~600-1200 char extracted snippet, not full article text (`include_raw_content` is never set). Fix bundle, no new provider needed: (1) qualify the query with the real company name, not just the ticker — requires fetching it via Polygon's `/v3/reference/tickers/{ticker}` (already-integrated key, no new cost) since `StockChange` currently only stores `ticker`; (2) switch `topic: 'news'` → `'finance'`; (3) `search_depth: 'advanced'` for better small-cap coverage; (4) narrow `start_date` to `beforeDate` minus ~30-45 days instead of 2000-01-01, accepting that thin-coverage names may return fewer/zero results rather than padding with stale context; (5) consider `include_raw_content: 'markdown'` for full article text, weighed against the added Claude input-token cost and the risk of pulling in more page boilerplate, not just more signal. Re-fetching the current 25-day/100-company test window after the fix costs approximately nothing (~100-200 Tavily credits, comfortably inside the 349 free credits left on the dev key); a full re-fetch across the whole cached history (337-560 days) would run ~$20-25 if ever needed.

- **`update-pick-price-series` refetches each pick's entire history every run instead of only new bars.** Fine at today's volume (1 pick/weekday, 2 total), but the real ceiling on refresh cadence is Polygon's free-tier 5-calls/min limit — one call per pick per run regardless of history size, so a full cycle takes `picks × 12s`. Switching to incremental fetch (only bars since each pick's last-stored point) shrinks payload/write size but does **not** raise that ceiling, since it's still one call per pick. To safely go more frequent than the current 30-min cadence as picks accumulate, the actual fix is scoping frequent refreshes to recent/"active" picks only and refreshing older, settled picks less often (e.g. once/day).
